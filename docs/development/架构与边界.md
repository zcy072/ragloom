# 架构与边界

本文说明 RAGLoom 的长期模块边界。存储细节见[数据与存储](./数据与存储.md)，运行链路见[文档处理与索引](./文档处理与索引.md)和[检索、问答与会话](./检索问答与会话.md)。

## 系统结构

```text
浏览器
  -> Nginx / Vue
  -> FastAPI routers
  -> application use cases / services
  -> Store、索引适配器、模型客户端
  -> SQLite、文件系统、Milvus、外部 API
```

后端入口是 [`backend/api.py`](../../backend/api.py)，应用装配入口是 [`backend/app_storage.py`](../../backend/app_storage.py)。业务实现按职责分为：

| 目录 | 职责 |
| --- | --- |
| `backend/routers/` | HTTP 参数、鉴权依赖、响应模型和 SSE 响应 |
| `backend/services/core/` | 配置、数据库 schema、依赖容器、模型配置和通用错误 |
| `backend/services/identity/` | 账户、角色、令牌和权限 |
| `backend/services/documents/` | 文档记录、解析、OCR、MinerU 和视觉内容 |
| `backend/services/indexing/` | 分块、持久化任务、锁和索引写入流水线 |
| `backend/services/retrieval/` | Milvus 索引适配、混合召回和上下文恢复 |
| `backend/services/chat/` | 查询规划、改写、重排、引用、会话和流式回答 |

主 RAG 依赖方向是：

```text
documents -> indexing -> retrieval -> chat
```

`core` 提供共享基础设施，`identity` 通过 router 依赖控制访问。不要让文档解析反向依赖聊天，也不要让服务层依赖 Vue 页面或 FastAPI 响应对象。

## HTTP 与业务边界

Router 应负责：

- 解析路径、查询参数、表单和请求体。
- 通过 `services.identity.auth` 执行身份与权限检查。
- 调用服务或用例，并声明稳定的 Pydantic 响应模型。
- 将流式生成器包装为 `StreamingResponse`。

跨 SQLite、文件系统、Milvus 和 MinerU 的操作必须由用例层协调。文档变更位于 `backend/services/documents/use_cases.py`，知识库生命周期位于 `backend/services/knowledge_bases/use_cases.py`。

服务层用 `backend/services/core/errors.py` 中的 `ApplicationError` 子类表达预期失败。`backend/api.py` 统一映射 HTTP 状态码和稳定错误码；核心服务不应构造 `HTTPException`。

## 依赖装配

`backend/app_storage.py` 创建进程级 Store，并通过路径回调读取 `DB_FILE`、`DATA_DIR` 等运行路径。回调而非冻结字符串使隔离测试可以切换临时存储而不重建所有对象。

`ApplicationContainer` 向聊天、检索和索引入口提供 Store、数据库路径和模型工厂。新增核心用例优先接收显式容器、Store 或回调；测试构造独立依赖，不要修改无关模块的全局状态。

运行时路径和模型常量的单一来源分别是：

- 路径与环境配置：`backend/services/core/settings.py`、`backend/services/core/config.py`、`backend/app_storage.py`。
- 外部模型客户端：`backend/services/core/llm_config.py`。
- 业务 Store：各领域的 `store.py` 或专用存储模块。

## 应用生命周期

FastAPI lifespan 按顺序启动：

0. 调用 `configure_logging`，挂接标准输出和文件日志。日志放在 lifespan 里而不是导入 `backend/api.py` 时配置，因为测试会导入 `api`，不能往部署环境的 `storage/logs/backend.log` 写入。
1. 验证主数据库 schema 版本（版本不匹配时不自动迁移，需删除 `storage/` 重建），处理模型密钥轮换，恢复中断任务、清除遗留的任务工作区并补齐默认记录。
2. 等待 Milvus 就绪并确保 collection 存在。
3. 创建进程级重排序客户端。
4. 启动索引 worker 线程池，并重新入队 SQLite 中的待执行任务。
5. 后台预热可用知识库的检索器缓存。
6. 启动每 24 小时一次的历史清理任务（`HISTORY_PRUNE_INTERVAL_SECONDS`），与启动时的清理相同。

退出时先停止 worker，再关闭共享网络客户端。新增后台资源必须有明确的启动、停止和异常恢复位置。

## 身份与权限

所有账户位于 `accounts` 表，角色是菜单和知识库权限的唯一来源。超级管理员没有代码级 `is_admin` 绕过，而是由受保护角色持有全部权限。

登录令牌包含稳定账号 ID、用户名、有效期和凭据指纹，不缓存角色权限。每次受保护请求都会重新读取账户状态和角色，因此停用账户、修改角色或修改密码会立即影响旧令牌。

`POST /api/register` 无需登录，只创建状态为“审核中”、没有角色的账户。登录要求状态为“正常”，所以必须由管理员先改状态；未分配角色的账户即使登录成功也没有任何菜单和知识库权限。限流规则见下方“登录与注册限流”。账号名称只能包含文字、数字和 `_ . @ -`，不能有空白字符；手机号选填，填写时须为 5～31 位数字（可带开头的 +、空格和 -）。

权限委派不能越级：给角色授权或给用户分配角色时，授予的权限不能超出操作者自己的权限；修改角色权限时，目标角色当前的权限也不能超出操作者；删除用户、修改其状态或角色时，目标账号当前的权限也不能超出操作者。`超级管理员` 角色的权限不能通过接口修改，也不能删除。知识库权限含“全公司”的账号视为拥有所有知识库权限，因此“全公司”是保留名称，新建或重命名知识库时都不能使用。

在部门知识库提问时，只有提问者能读取“通用知识库”才会补充检索它，规则和其他知识库一致；希望全员都能用到通用材料，就给所有角色勾选“通用知识库”。是否补充由 `backend/routers/chat.py` 按提问者权限决定，检索缓存按“是否补充”分开存放。“通用知识库”不能删除或重命名（`common_knowledge_base_protected`），它只在空数据库初始化时创建，删除后补充检索会静默失效。

登录时用户名不存在也会对一个固定的假哈希执行一次 bcrypt 校验，响应时间与密码错误时一致，不能借此判断用户名是否存在。

### 用户分析与对话查看

`用户分析` 菜单权限可以看到概览、用户列表和单用户详情（`backend/routers/user_analytics.py`、`backend/services/analytics/`）。提问、会话和评价统计只覆盖查看者可读的知识库，账户数和登录统计不分知识库。问题预览与 `运行监控` 一样只有前 200 字。

打开某个用户的完整对话另需 `查看用户对话` 权限，它不对应菜单。读取时依次检查：

1. 目标账号的权限不能超出查看者（与用户管理相同的不越级规则），否则返回 403；
2. 会话必须属于该用户，且所在知识库查看者可读，否则统一返回 404，不暴露会话是否存在；
3. 在同一事务中写入 `admin_audit_log` 再返回内容，审计列表在页面底部，有 `用户分析` 权限即可查看。

前端菜单隐藏只改善体验，后端的权限依赖才是安全边界。会话按 `account_id` 归属，并固定绑定一个知识库；继续、读取和删除会话时都会重新校验所有权与当前知识库权限。

### 登录与注册限流

实现位于 `backend/services/identity/rate_limit.py`，在 `backend/routers/auth.py` 接入，超限返回 `429` 并带 `Retry-After`。

- 登录按用户名限制失败次数（统一小写、去空格，账号存不存在都一样计数，避免靠限流判断账号是否存在）：默认 15 分钟内 5 次，达到后即使密码正确也拒绝，且被拒绝的请求不再校验密码、不延长锁定。登录成功清零该用户名的计数。
- 登录同时按来源地址限制失败总数：默认 5 分钟内 20 次，用来拦截一个密码试很多用户名。
- 注册按来源地址限制提交次数，无论成功与否：默认 1 小时内 5 次。
- 只有凭证错误计入失败；账号处于“审核中”说明密码已正确，不计入。
- 记录的键数量有上限，提交大量不同用户名不会无限占用内存。
- 用户自己设置的新密码（注册和改密）至少 8 个字符，下限在 `backend/services/core/config.py::MIN_PASSWORD_LENGTH`，前端表单有相同提示；初始管理员密码来自部署配置，不受此限。密码按 UTF-8 字节计算，不能超过 72 字节（bcrypt 的输入上限，约 24 个汉字）。注册和改密超出时返回 422 和明确提示，而不是静默截断；登录时超长密码只会校验失败。
- 次数或窗口设为 0 即关闭对应限制，参数见[配置项](配置项.md)。

来源地址默认取连接地址。`X-Real-IP` 可被直接访问后端的客户端伪造，因此后端代码默认不信任它；`docker-compose.yml` 默认设置 `AUTH_TRUST_X_REAL_IP=true`，因为 Compose 里后端的 8000 端口只绑定 `127.0.0.1`，外部请求都经 Nginx，该请求头由 Nginx 写入。若改成对外暴露 8000 端口，来源地址限制可被绕过，必须把该项设为 `false`。用户名锁定不依赖来源地址。

问答按账号限流（`backend/services/identity/rate_limit.py::ChatRequestLimiter`，在 `backend/routers/chat.py` 接入）：每个账号同时最多 `CHAT_USER_MAX_CONCURRENT`（默认 2）个流式回答，每分钟最多 `CHAT_USER_PER_MINUTE`（默认 10）次提问，超限返回 429，错误码分别是 `chat_concurrency_limited` 和 `chat_rate_limited`。回答流结束、出错或客户端断开时释放名额；万一漏了释放，名额 15 分钟后自动作废。被拒绝的请求不计入每分钟次数。设为 0 即不限，计数在进程内存中，重启后清零。

用户名锁定可被他人利用：故意输错几次就能让对方的账号暂时无法登录。这是 Demo 取舍，需要更强防护时应改用“用户名 + 来源地址”联合计数。

跨模块结构集中在各领域的契约模块：

| 文件 | 主要契约 |
| --- | --- |
| `backend/services/core/contracts.py` | 模型、检索和知识库配置 |
| `backend/services/documents/contracts.py` | 文档记录、元数据和筛选 |
| `backend/services/indexing/contracts.py` | 持久化索引任务 |
| `backend/services/identity/contracts.py` | 账户、角色和认证主体 |
| `backend/services/chat/contracts.py` | 聊天请求和来源 |

Store 应把 SQLite 行集中转换为明确契约。业务代码不要依赖列下标元组，也不要跨模块返回字段不明的裸 `dict`。稳定的新契约应加入 `backend/pyproject.toml` 的渐进 Pyright 范围。

## 多资源一致性

SQLite 事务无法覆盖文件系统和 Milvus，因此代码使用提交顺序、锁、原子发布和补偿保证可恢复状态：

- 先创建可恢复的 SQLite 任务，再唤醒内存 worker；内存队列不是事实来源。
- 上传先写同目录临时文件，校验完成后用 `os.replace` 原子发布。
- 单文件变更使用文件锁（共享知识库），整库变更使用知识库独占锁，见[文档处理与索引](./文档处理与索引.md)的“两级锁”。
- 同名上传用当前任务 ID 判断版本，旧任务不能覆盖新文件状态。
- 父块表与 Milvus 的发布顺序固定为先父块、后 Milvus，删除顺序相反；两者不是原子操作，异常由重建覆盖。
- Milvus 按来源提交新 generation，成功后清理旧 generation；失败则撤销新 generation。
- 索引以不可变的 `kb_id` 为键，知识库改名只补偿文件目录和 MinerU 目录的移动，不涉及索引。
- 删除知识库先清理 Milvus 和父块表；索引失败时保留权威关系数据，避免“接口失败但数据已删一半”。

文档筛选元数据只保存在主 SQLite。查询时先计算来源白名单，再交给 Milvus 作为过滤条件，因此修改类型、标签或生效日期不需要重建正文索引。

## 前端边界

`frontend/src/apiClient.js` 统一处理认证、JSON 响应和 API 错误。带令牌请求收到 `401` 时会清理本地会话并触发 `auth-expired`；但只有存储里的令牌仍是该请求发出时使用的那份才会清理，其他标签页已经换成新令牌时，旧请求的 `401` 不会误清新会话。`App.vue` 监听 `storage` 事件，其他标签页退出登录会让本标签页同步回到登录页，换了账号则重新载入。

菜单权限在登录时随响应返回，之后由 `GET /api/me` 返回实时角色与权限，前端启动和标签页重新可见时刷新一次，管理员改了角色后不必等令牌过期。后端的权限校验本来就是实时的，这只是让界面菜单跟上。

聊天 SSE、会话列表、文档列表和预览逻辑集中在 composables。网络、Store 和通知通过可选参数注入，Node 单元测试使用假依赖验证协议与状态；布局、浏览器 API 和跨页面流程由 Playwright 验证。

## 已知边界

- 索引 worker 与 FastAPI 位于同一进程，只适合本地或单实例演示，不是跨进程任务系统。
- 主数据库没有声明外键，跨表删除完整性由 Store 和用例负责。
- 登录与注册限流的计数在进程内存中，重启清零，多进程或多实例部署需要改为共享存储；MFA、SSO、通用操作审计和多实例密钥管理不在当前 Demo 范围内（审计只覆盖查看用户对话）。
- 嵌入固定依赖 SiliconFlow；重排序默认 SiliconFlow，可用 `RERANK_BASE_URL` 换成兼容接口（见[检索问答与会话](./检索问答与会话.md)）；聊天模型可使用 OpenAI 兼容提供商。
- 认证层和部分路由直接抛 `HTTPException`，响应里没有 `code` 字段；前端按 `detail` 显示错误，统一 `code` 要连带改前端和 OpenAPI 快照，暂不处理。
- `backend/routers/ops.py`、`backend/routers/documents.py`、`backend/routers/knowledge_bases.py` 直接引用 `app_storage`，绕过 container；不影响功能和测试隔离，只是分层不统一。
- 用户分析的统计实时聚合，没有预聚合表，统计范围上限 90 天；数据量大到查询变慢时再按天预聚合。
- `get_settings()` 每次调用都重新解析环境变量，每次调用模型都新建客户端；开销相比一次模型调用可忽略，缓存会让测试中替换配置失效。

修改这些边界时，测试要求见[开发与交付](./开发与交付.md)。
