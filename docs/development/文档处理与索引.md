# 文档处理与索引

本文描述上传文件从接收、解析、分块到写入 Milvus 索引的完整链路。存储结构见[数据与存储](./数据与存储.md)。

## 支持范围

正式支持的扩展名由 `backend/services/documents/types.py` 定义：

| 类型 | 解析方式 |
| --- | --- |
| PDF | 本地文本、MinerU 云端、PaddleOCR |
| DOCX | 本地结构解析、MinerU 云端 |
| Markdown、TXT | 本地文本解析 |
| PNG、JPG、JPEG | 视觉模型，失败时回退 PaddleOCR；也可直接选择 PaddleOCR |

单个上传文件不能超过 50 MiB。新上传的文件名按 UTF-8 计不能超过 200 字节（约 66 个汉字），因为上传临时文件和 MinerU 结果目录会在文件名后追加后缀，文件系统单级名称上限是 255 字节；超出时返回 422。传统 `.doc`、CSV、Excel 和 XSD 不在支持范围内；需要精确聚合、计算或结构化筛选的数据应走专门查询链路。

## 上传与任务创建

上传接口为 `POST /api/documents/{kb_name}`，业务编排位于 `backend/services/documents/use_cases.py`：

```text
校验知识库、文件名、扩展名、解析方式和元数据
  -> 分块读取到同目录临时文件，并检查大小
  -> 获取该文件的锁（共享知识库）
  -> os.replace 原子发布正式原文件
  -> 创建 queued 索引任务
  -> 写入或更新 documents，状态设为 processing
  -> 唤醒进程内 worker
  -> 返回 job_id
```

同一知识库中的 `kb_name + filename` 唯一。再次上传同名文件代表替换来源，会同步更新文件、元数据、解析方式和当前任务 ID。

HTTP 请求不等待解析、OCR、嵌入和索引写入完成。解析阶段不持锁，准备和发布阶段只锁当前文件（见下文“并发执行”），所以任务运行期间，同一知识库的上传、改元数据、改解析方式和删除请求只会在操作同一个文件时等锁；全库重建的登记与收尾、删除和重命名知识库会独占整个知识库，这时这些请求才都要等。前端根据文档和任务状态展示：

```text
queued -> running -> completed / failed / superseded / interrupted
document: processing -> ready / error
document（重建）: ready -> rebuilding -> ready / error
```

具体任务状态常量以 `backend/services/indexing/jobs.py` 为准。

## Worker 与恢复

`backend/services/indexing/worker.py` 中的 `IndexWorker` 使用固定数量的后台线程并行执行任务，线程数由 `INDEX_WORKER_THREADS` 决定（默认 3，范围 1 到 8，设为 1 即串行）。内存队列只负责唤醒，SQLite 的 `index_jobs` 才是事实来源；一个任务只会被一个线程执行，由内存去重和 `index_jobs.start` 的原子状态迁移共同保证。

启动时会重新入队持久化的待执行任务，处理上次进程中断留下的状态，并清除遗留的任务工作区。任务在准备阶段和发布阶段都会确认它仍拥有文档的最新版本，因此旧的同名上传任务不能覆盖新文件状态。

支持三类操作：

- `process`：解析并更新单个文档索引。
- `rebuild`：重新解析知识库中的所有原文件并发布完整索引。
- `delete`：删除指定来源的两类索引。

当前设计适合单进程演示。多个 FastAPI 进程不能依靠这个内存队列实现可靠的分布式调度。

## 并发执行

`process` 任务拆成准备、阶段 A、发布三步，只有首尾两步持锁（`run_document_job`）：

```text
准备（文件锁，很短）  确认任务归属 -> 为原文件创建快照 -> 固定解析方式与分块配置
阶段 A（不持锁）      解析/OCR/视觉 -> 切分 -> 再次确认归属 -> 计算嵌入向量
发布（文件锁）        再次确认归属 -> 发布结果目录 -> 写父块表 -> 写 Milvus -> 清检索缓存 -> 更新状态
```

**两级锁。** `backend/services/indexing/locks.py` 提供两种锁。`document_lock(kb, filename)` 共享知识库、独占一个文件，用于上传、删除、改元数据、改解析方式和索引任务的准备与发布；`knowledge_base_lock(kb)` 独占整个知识库，用于删除、重命名知识库以及重建的登记和收尾。不同文件的发布可以同时写 Milvus，整库操作会等所有单文件操作结束。整库锁写优先，它在等待时新的单文件操作排在它后面，批量上传不会让删除知识库一直等下去。获取顺序固定为先知识库、后文件，两种锁都不可重入。锁在进程内，只适用于单进程部署。

批量上传时这把锁的影响在本地压测过（200 个文档，每个 600 个子块，假解析和假嵌入，真实 Milvus）：原先所有操作共用一把知识库锁，8 个 worker 时上传接口 p95 为 4.4 秒、发布等锁最长 7.7 秒；改为文件锁后，同一知识库内不同文件不再互相等待，上传接口 p50 为 16 毫秒，全部就绪从约 250 秒降到 132 秒。p95 仍有约 1.4 秒，来自 Milvus 和 SQLite 写入本身的竞争。单机 Milvus 的写入速度是吞吐上限，worker 加多后单次发布会变慢。

**任务工作区。** 解析期间同名文件可能被重新上传或删除，MinerU 结果和视觉缓存的路径又由原文件路径推导，所以阶段 A 不能直接读写正式路径。准备阶段把原文件硬链接（失败则复制）到 `data/<知识库>/.index_jobs/<job_id>/`，并把已有的视觉缓存复制进对应的任务私有结果目录；阶段 A 只读写这两处。发布时，任务结果目录通过重命名替换文档的正式 MinerU 结果目录，替换失败会恢复旧目录。任务结束后无论成败都会删除工作区，启动时也会清除遗留的 `.index_jobs`（`backend/services/indexing/workspace.py`）。上传总是通过 `os.replace` 原子替换文件，所以硬链接快照不会被后续上传改动。

**归属校验。** 校验必须在发布阶段的锁内重做。阶段 A 期间文档被重新上传、删除或被重建任务重新标记，旧任务都会以 `superseded` 结束，且不写任何索引、不发布结果目录。阶段 A 在调用嵌入前还会不持锁地检查一次，已被替代的任务直接结束，不再消耗嵌入配额；这次检查只是提前放弃，最终以发布阶段锁内的校验为准。

**任务收尾。** 每个任务结束都要确认知识库没有在解析期间被删除，否则要清理任务重新创建的目录。知识库仍在时直接返回，不获取整库锁；判断为已删除后才持锁复核并清理。

**嵌入先于写入。** 向量只取决于分块文本，与 `chunk_index` 无关，所以在阶段 A 用 `embed_splits` 计算，发布时 `ChunkIndex.publish_source(..., vectors)` 直接使用已算好的向量。阶段 A 嵌入失败时不降级，异常直接抛出，文档进入 `error` 并带上原因，索引不被修改。

**Milvus 发布。** `publish_source` 在写入前查出该文件旧代的主键，写入新代后按主键删除旧代。collection 是强一致性，紧接在写入后按条件查询或删除要等这批写入可见（600 条约 1.7 秒），按主键删除不需要等。写入前查询依赖调用方持有文件锁，否则两个发布交错会留下没被查到的旧代。

**重建。** `rebuild` 与上传共用同一套“持锁准备、无锁解析、持锁发布”流程，各文档按 `INDEX_WORKER_THREADS` 并行处理，每个文档发布完成就立刻写回自己的状态，前端能看到它逐个变成就绪。`run_rebuild_job` 只在开头（登记任务）和结尾（清理过期向量和父块、更新任务状态）持整库锁，中间各文档的处理不持有知识库锁，其余请求不会被长时间阻塞。重建期间已完成阶段 A 的 `process` 任务，会在发布阶段发现文档已被重新标记而按 `superseded` 结束。

**Milvus 不可用。** Milvus 是外部服务。启动时后端会等待它就绪（`ensure_collection`，带重试）。运行中写入失败，文档进入 `error`；检索失败会向上抛出明确错误，不再静默返回空结果。恢复后重新上传或重建即可。

### 限制与未验证项

- 知识库有正在执行的任务时，重命名会被拒绝（`knowledge_base_has_running_jobs`，见 `backend/services/knowledge_bases/use_cases.py`），因为移动目录会让任务丢失源文件快照；等任务结束后重试。解析期间删除知识库是允许的，任务按 `superseded` 结束。
- 并行解析会抬高内存峰值，大 PDF 同时解析时需要观察。
- 各项并发默认值是按常见云端配额估算的，需要按实际账号限流调整。
- 任务快照优先使用硬链接，文件系统不支持时回退为复制，大文件会多占一份临时空间。
- 锁的压测用的是假解析和假嵌入；真实解析下并行的耗时收益、429 频率和内存峰值没有实测。每个任务结束时的分阶段耗时日志可用于做这次对比。

### 资源限流

线程数只决定能同时处理多少文档，各类资源另有进程级上限（`backend/services/core/concurrency.py` 的 `resource_slot`），所有索引任务合计计算：

| 环境变量 | 默认 | 范围 | 限制对象 |
| --- | --- | --- | --- |
| `INDEX_WORKER_THREADS` | 3 | 1 到 8 | 同时处理的文档数 |
| `OCR_MAX_CONCURRENCY` | 1 | 1 到 4 | PaddleOCR 推理；引擎线程安全性未验证，默认单次推理 |
| `MINERU_MAX_CONCURRENCY` | 3 | 1 到 8 | MinerU 云端解析，覆盖上传、轮询和下载 |
| `EMBEDDING_MAX_CONCURRENCY` | 2 | 1 到 8 | 嵌入请求 |
| `VISION_GLOBAL_MAX_CONCURRENCY` | 6 | 1 到 32 | 所有文档合计发往视觉模型的请求；单个文档内的线程池也取此值，没有单独的文档内上限 |

建索引用的嵌入客户端重试次数设为 5、请求超时 120 秒，用于吸收并行带来的偶发 429。在线提问的查询嵌入使用同一模型但另建客户端（`get_query_embeddings`），超时 15 秒、重试 1 次，用户在等待回答时失败要尽快暴露。

每个任务结束时会输出一行日志，包含阶段 A 总耗时及 `parse`、`split`、`embed` 各自耗时、等锁时间和发布耗时，可用来判断瓶颈和调整上限。

## 解析策略

解析入口位于 `backend/services/documents/loaders.py`，统一返回两类内容集合：

```text
DocumentRoutes
  fixed       稳定的正文页或文本段
  structured  带标题层级、表格和结构元数据的段落
```

### PDF

- `native_text` 使用 PyPDF 提取文本，适合有可复制文本层的 PDF。
- `mineru_cloud` 上传原文件到 MinerU，使用结构化 Markdown、表格和图片产物。
- `paddle_ocr` 将页面转为图片后在本地 OCR，适合扫描版 PDF。页面按页渲染（每次只在内存里保留一页的图片），页数很多的扫描件不会因此占满内存。

本地文本模式没有提取到有效内容时，任务会明确提示改用 MinerU 或 PaddleOCR，不会静默切换解析方式并改变数据外发边界。

### DOCX、Markdown 与 TXT

DOCX 本地解析保留段落、标题和表格；也可使用 MinerU。Markdown 同时进入普通正文和结构化路线，TXT 主要进入固定路线。文本读取失败会作为任务错误保存，不产生空索引。

### 图片与视觉内容

独立图片默认使用视觉模型生成可检索描述，并用 PaddleOCR 补充可见文字；视觉调用失败时回退本地 OCR。MinerU 从文档中提取的流程图、示意图和复杂表格也可生成 `visual` 路线。

视觉结果及其 OCR 内容可能包含敏感信息。是否发送到外部服务由 `RAG_IMAGE_ANALYSIS`、模型提供商配置和用户选择共同决定。

## 三条分块路线

索引流水线在所有解析成功后生成互补切片：

### `fixed`

先按知识库的 `chunk_size` 和 `chunk_overlap` 生成父块，再切成更聚焦的子块。子块进入召回索引，父块保存于主 SQLite 的 `parent_chunks`；命中后通过 `parent_id` 恢复完整语境。

默认父块参数是 800/150，单一来源为 `backend/services/core/config.py`。分隔符优先使用段落、换行和中文句末符，再降级到空格或字符边界。

### `structured`

根据 Markdown、DOCX 或 MinerU 的标题层级组织章节，并把标题链作为 `contextual_title`。表格会尽量保留表头、行关系和邻近正文，使章节或表格自身可以成为完整证据。

### `visual`

把图片描述、OCR 文字和视觉元数据组织成文本证据。它用于补充正文路线，不保证对数值密集表格进行精确计算。

不同路线可能包含相同原文。索引阶段保留这种冗余以提高召回率，检索阶段再按正文重叠、来源、父块和路线去重。

## 索引发布顺序

单文档处理分为准备、阶段 A、发布三步（见上文“并发执行”）。发布步骤内部的顺序是：

1. 阶段 A 已完成所选解析方式、视觉补充、全部切分和嵌入；空结果立即失败，尚不修改索引。
2. 发布时在锁内先写父块表（同一事务先删后插该来源的旧记录）。
3. 再调用 `publish_source` 写入 Milvus：分批插入新 generation，成功后删除同来源的旧 generation，并清除检索器缓存。

Milvus 写入失败时，新 generation 会被撤销，旧版本保持可用，文档标记为 `error`。进程恰好在写入新 generation 之后、删除旧 generation 之前崩溃，可能留下重复记录；重新处理该文档或完整重建会清理。

完整重建不预先清空索引。登记时原本就绪的文档标为 `rebuilding`，它们的旧版本继续参与检索；其余文档标为 `processing`。每个文档像上传那样发布：`publish_source` 先写入新版本、再删除旧版本，所以重建期间知识库始终可检索，每个文件在发布那一刻切换到新版本。已保存的 MinerU 结果会被复用，不再重新上传云端。全部文档处理完后，再删除不属于任何就绪文档的旧向量和父块（`delete_stale_sources`），解析失败的文档的旧版本在这一步删除。

重建按文档隔离失败：某个文件解析失败（例如 PDF 超过 MinerU 的 200 页上限）时，该文档记为 `error` 并带上自己的原因，其余文档照常变为 `ready`，重建任务记为完成，任务消息提示失败数量。只有所有文件都失败时，任务才记为失败。

重建中途进程重启时，已完成的文档保持就绪，其余文档（包括 `rebuilding`）按重启规则标为出错，不再参与检索，需要再次重建。

**MinerU 页数预检。** 上传到云端前先用 pypdf 读取页数，超过 200 页直接报错并提示拆分文件或改用原生文本 / Paddle 本地 OCR，不占用云端解析名额。读不出页数的文件（损坏、加密）不拦截，交给 MinerU 判断。预检在解析器路径内执行，因此上传和重建都适用，且上传接口本身不拒绝文件。

## 变更与删除

### 元数据更新

文档类型、标签和生效日期是主 SQLite 中的筛选元数据。更新它们不会解析文件、切分或生成向量。

### 解析方式更新

PDF、DOCX 和图片可以修改解析方式。系统保存新选择并创建新的 `process` 任务；其他文本类型不允许切换解析器。

### 删除文档

```text
获取该文件的锁
  -> 创建持久化 delete 任务
  -> 删除 MinerU 结果
  -> 删除原文件和 documents 记录
  -> 清除检索缓存
  -> worker 依次删除 Milvus 记录和父块表记录；没有任何文档时删除整个 collection
```

删除任务执行时会确认同名文件没有被重新上传，防止旧删除任务清掉新索引。

### 修改分块配置

修改 `chunk_size` 或 `chunk_overlap` 会改变所有切片边界，因此必须创建整库 `rebuild` 任务。查询改写开关只影响提问，不触发重建。`chunk_overlap` 可以为 0（相邻切片不重叠），0 是有效设置，不会被当成未配置而换回默认值。

## 视觉模型配置

适用于独立图片，以及 MinerU 提取的流程图、示意图等视觉内容。变量默认值以 `backend/services/core/settings.py` 为准，列表见[配置项](配置项.md)。

### 分析策略

`RAG_IMAGE_ANALYSIS` 控制处理方式，留空或填无效值按 `auto` 处理：

| 值 | 行为 | 适用场景 |
| --- | --- | --- |
| `auto`（默认） | 先用视觉模型理解图片，失败回退 PaddleOCR，不阻塞索引；分析结果有缓存 | 需要理解图表、流程图，且允许图片发送到外部模型 |
| `ocr` | 只用 PaddleOCR 提取文字，能检索图中文字，但没有图表语义描述 | 数据不能外发，或图片主要是文字截图 |
| `disabled` | 独立图片返回空文档，MinerU 视觉内容返回空列表，图片内容无法检索 | 纯文本知识库 |

`disabled` 只影响视觉内容，不影响 MinerU 提取的文本、表格和公式。

### 配置视觉模型

视觉分析走 OpenAI 兼容接口，所选模型必须支持图片输入；是否支持、接口地址和计费以服务商文档为准。

1. 在“模型管理”新增提供商，填写名称、API Key、接口地址和模型。
2. 把 `.env` 中的 `RAG_VISION_PROVIDER` 设为与该提供商完全相同的名称。
3. 用 `docker compose up -d backend` 重新创建后端容器（`restart` 不会重新读取 `.env`）。

`RAG_VISION_MODEL`、`RAG_VISION_BASE_URL`、`RAG_VISION_API_KEY` 是可选覆盖项，非空时覆盖提供商保存的对应字段。推荐留空，让配置只在“模型管理”维护一处。切换提供商时必须清空这三项，否则请求仍会发往旧服务。

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `RAG_VISION_PROVIDER` | `OpenAI` | 必须与“模型管理”中的提供商名称完全一致 |
| `RAG_VISION_TIMEOUT_SECONDS` | 60 | 单次请求超时，范围 10 到 180 |
| `VISION_GLOBAL_MAX_CONCURRENCY` | 6 | 所有文档合计同时发往视觉模型的请求数，范围 1 到 32 |

### 实现要点

图片编码为 base64 data URL，以 `image_url` 消息发送，限制为最长边 2600 像素、5 MiB；请求参数为 `temperature=0`、`max_completion_tokens=2200`、`max_retries=0`（`backend/services/documents/visual_vision.py`）。

提示词要求：按类型转写（表格还原行列，流程图按顺序写节点与分支，统计图写坐标轴与读数）；名称、编号、数字、单位原样抄录，图上的英文等外文照原文写、不翻译（否则之后用英文术语检索不到），看不清写“（无法辨认）”；输出严格 JSON（`indexable`、`kind`、`title`、`content`），content 能脱离图片理解且不超过 1000 字；图片内的文字不当作指令。

修改提示词时同步递增 `backend/services/documents/visual_cache.py` 里的 `VISUAL_PROMPT_VERSION` 和 `STANDALONE_IMAGE_PROMPT_VERSION`。缓存键包含这两个版本，递增后旧缓存失效，下次解析或重建会重新调用视觉模型。

### 验证与排查

视觉调用成功时不输出日志，所以“没有日志”不等于“没走视觉模型”。用回退告警判断：

```bash
docker compose logs backend | grep -i "OCR fallback"
```

- 出现 `using OCR fallback`（独立图片为 `Standalone image visual model unavailable ...`，MinerU 图片为 `MinerU visual model unavailable ...`）：视觉调用失败并已回退本地 OCR，告警末尾带具体错误。
- 出现 `视觉模型提供商未配置完整：<名称>`：`RAG_VISION_PROVIDER` 在“模型管理”里找不到同名提供商，或该提供商的 API Key、接口地址、模型有缺项。
- 出现 `视觉模型未返回约定的 JSON 结构`：系统会尝试从回复中提取 JSON；仍失败时检查所选模型是否真的支持图片输入。
- 都没有，且上传图片后能检索到语义描述，可认为工作正常。`ocr` 和 `disabled` 模式不产生此类告警。

调用失败时依次检查：提供商名称与三项配置是否完整、`.env` 是否残留上一个提供商的覆盖项、模型是否支持图片、容器内网络（`docker compose exec backend curl -I <接口地址>`）。分析结果不理想通常来自分辨率过低或被压缩过度、图片过于复杂，或 MinerU 提取的图注、HTML 上下文不完整。

## 故障排查

按以下顺序定位文档无法使用的问题：

1. 查看文档的 `status` 和 `error_message`。
2. 查看该知识库最近的 `index_jobs`，确认任务是否被替代或中断。
3. 查看后端日志中的解析、OCR、嵌入和 Milvus 异常。
4. 确认原文件仍存在于 `storage/data/<知识库>/`。
5. 检查所选解析器的外部配置和数据外发限制。
6. 若索引 schema 或嵌入模型变化，执行完整重建，不要手工修改索引文件。

涉及索引变更的测试与交付要求见[开发与交付](./开发与交付.md)。
