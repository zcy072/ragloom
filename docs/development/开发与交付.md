# 开发与交付

本文是开发命令、测试范围、维护规则和交付标准的唯一入口。架构约束见[架构与边界](./架构与边界.md)。

## 环境原则

项目以 Docker Compose 为标准运行环境。后端镜像只复制应用源码，不包含 `backend/tests/`；Compose 运行时只挂载 `storage/`。因此：

- 修改 Python 后，现有运行容器不会自动看到工作区源码，必须重建镜像。
- 后端测试必须把工作区挂载到 `/app`，不能用 `docker compose exec backend pytest`。
- 前端依赖和 Chromium 由测试镜像提供，不要求宿主机保留 `frontend/node_modules` 或安装浏览器。
- 宿主机只需要 Docker Compose 和常见 Shell 工具；Python、Node、Ruff、Pyright 和浏览器依赖均由镜像提供。

镜像构建阶段由 root 安装的 Python、Node 和系统依赖属于不可变镜像层，运行时只读使用，不需要也不应该由 `app` 用户删除。应用实际写入的只有宿主机 `storage/` 和 Docker 命名卷 `pymodel_paddle_models`；Compose 已按 `1000:1000` 的应用用户准备这些路径。Docker 的镜像和构建缓存由 Docker 管理，不要直接操作其内部目录。

## 常用命令

启动或重建全部服务：

```bash
docker compose up -d --build
docker compose ps
```

运行完整质量检查：

```bash
./scripts/check.sh
```

该脚本依次运行 Docker 镜像构建、后端静态检查（Ruff、Pyright、Python 编译）、后端测试、前端检查和 Nginx 配置检查。Playwright 浏览器测试默认跳过，交给 GitHub CI；需要在本地跑时用 `./scripts/check.sh --e2e`（会拉取约 3.7GB 的 Playwright 镜像）。

## 后端验证

全量测试使用标准库 `unittest`：

```bash
docker compose run --rm --no-deps -v "$PWD:/repo" -w /repo/backend \
  -e PYTHONPYCACHEPREFIX=/tmp/pymodel-pycache backend \
  python -m unittest discover -s tests -v
```

运行单个模块或测试时，把 `discover -s tests` 换成 `tests.test_chat_service` 或 `tests.test_chat_service.ChatServiceTest.test_name`。

单独运行后端静态检查：

```bash
docker compose build backend-check
docker compose run --rm --no-deps backend-check
```

Ruff、Pyright 和 Python 编译检查都在 `backend-check` 镜像中执行，不会在仓库生成 `.uv-cache`、`.uv-tools` 或宿主机虚拟环境。

测试工作区源码后，仍需重建后端并检查启动日志：

```bash
docker compose up -d --build backend
docker compose logs backend --tail=20
```

这一步用于发现 backend/Dockerfile 复制范围、导入名和镜像启动阶段的问题。

排查线上问题优先用管理员账号打开“运行监控”页面：依赖状态（SQLite、Milvus 是否可查询及错误详情）、概览、慢请求与失败的问答记录、失败的索引任务和日志末尾都在那里。`/api/health` 只表示进程存活，Compose 健康检查用它；`/api/ready` 无需登录，SQLite 和 Milvus 都能查询时返回 200，否则返回 503 并只标出哪一项异常，适合负载均衡或外部监控探测。需要完整日志时读 `storage/logs/backend.log`（容器重建后仍在，详见 [数据与存储](数据与存储.md)）；`docker compose logs backend` 仍可看到同样的标准输出。每行日志在级别之后带方括号中的请求 ID：HTTP 请求的 ID 也放在响应头 `X-Request-ID` 里，问答的追踪 ID 与它相同，所以从运行监控页的一条问答记录可以直接搜到这次请求的全部日志；索引任务的日志带任务 ID；不属于任何请求或任务的行显示 `-`。

需要隔离存储的测试继承 `backend/tests/support.py` 中的 `IsolatedStorageTestCase` 或 `IsolatedStorageAsyncTestCase`。不要在新测试中重复修改和恢复全局路径。

## 前端验证

完整前端静态检查、类型检查、Node 单元测试、构建和依赖审计：

```bash
docker compose build frontend-check
docker compose run --rm --no-deps frontend-check
```

浏览器测试：

```bash
docker compose build e2e
docker compose run --rm --no-deps e2e
```

API client 与 composable 的纯状态和协议行为放在 `frontend/tests/unit/`；布局、浏览器 API 和跨页面工作流放在 `frontend/tests/e2e/`。

升级 `@playwright/test` 时，必须同步修改：

- `frontend/package.json` 和 `frontend/package-lock.json`。
- `frontend/Dockerfile.e2e` 中的 Playwright 镜像标签。

## OpenAPI 契约

`backend/tests/openapi_snapshot.json` 是完整 API schema 快照，`backend/tests/test_openapi_snapshot.py` 在每次跑全量测试时比对它，接口有任何变化测试都会失败。

有意修改接口后重新生成并审阅差异：

```bash
docker compose run --rm --no-deps -v "$PWD:/repo" -w /repo/backend \
  -e PYTHONPYCACHEPREFIX=/tmp/pymodel-pycache -e UPDATE_OPENAPI_SNAPSHOT=1 backend \
  python -m unittest tests.test_openapi_snapshot
git diff -- backend/tests/openapi_snapshot.json
```

不要为了让测试通过而直接接受未审阅的 schema 变化。

## 依赖锁定

Python 依赖声明在 `backend/pyproject.toml`：运行时直接依赖在 `[project] dependencies`，检查镜像用的 ruff、pyright、uv 在 `[dependency-groups] check`。Docker 构建不读取 `backend/pyproject.toml`，只安装两个带 hash 的锁文件：`backend/requirements.lock`（运行时完整闭包）和 `backend/requirements-check.lock`（检查工具，以运行时锁文件为约束，保证共有依赖版本一致）。修改依赖后在检查镜像里重新生成：

```bash
docker compose build backend-check
docker compose run --rm --no-deps backend-check sh -c '
  uv pip compile pyproject.toml --output-file requirements.lock \
    --python-version 3.12 --generate-hashes --index-url https://pypi.org/simple &&
  uv pip compile --group check --constraint requirements.lock \
    --output-file requirements-check.lock \
    --python-version 3.12 --generate-hashes --index-url https://pypi.org/simple'
```

镜像构建使用 `pip install --require-hashes`。hash 按官方 PyPI 生成；`PIP_INDEX_URL` 换成镜像源时，只要镜像内容与 PyPI 一致就能通过校验，被篡改或不完整的包会让构建失败。uv 的解析缓存写入容器临时目录，宿主机不需要安装 uv。项目不使用 `uv.lock`，不要同时维护两套锁文件。

前端使用 `package-lock.json` 和 `npm ci`。不要使用破坏性的 `npm audit fix --force` 代替依赖升级和兼容性验证。

`frontend/package.json` 的 `overrides` 把 `minimatch` 固定在 11.0.5：eslint 依赖的 `@eslint/config-array` 把它限制在 `^10.2.4`，而 7.0.0–11.0.0 有 GHSA-g3hv-75wg-m249（只影响开发期的 lint，不进入前端镜像）。等 eslint 自己升到修复版本后，可以删掉这条覆盖。`npm audit` 偶尔会因访问 npmjs.org 超时而回退到已下线的旧接口并报 400，重试即可，不是依赖问题。

Ruff 当前执行语法、导入和高价值正确性规则。Pyright 采用渐进范围；完成新的稳定跨模块契约后，应把相应模块加入 `backend/pyproject.toml`，不要通过放宽全局规则或无依据的 `Any` 消除诊断。

## 部署冒烟

涉及容器、挂载、权限或持久化的变更，在实际服务启动后运行：

```bash
SMOKE_ADMIN_PASSWORD='<current-admin-password>' ./scripts/smoke-test.sh
```

脚本创建唯一命名的临时知识库，验证登录、上传、索引、读取、删除和服务重启恢复，并清理临时数据。它不会使用已有知识库，但会短暂重启容器。

## 变更规则

### HTTP API

- 使用明确的 Pydantic 请求和响应模型。
- 保持字段、状态码和稳定错误码兼容；有意变化时更新并审阅 OpenAPI 快照。
- Router 只做协议、权限和错误转换，业务流程进入 service 或 use case。

### 跨资源操作

- 明确 SQLite、原文件、父块表、Milvus、MinerU 和缓存的提交顺序。
- 复用知识库级锁、原子发布和现有补偿机制。
- 测试成功路径、关键失败阶段和最终持久化状态，不能只断言 HTTP 响应。

### 后台任务与并发

- SQLite 任务记录是事实来源，内存队列只负责调度。
- 覆盖重复提交、同名版本替代、进程中断和失败恢复。
- 旧任务不得覆盖新文档状态或删除新索引。

### 前端异步状态

- composable 通过参数注入网络、Store 和通知依赖。
- 覆盖 `401`、`412`、SSE 跨分片、终态、连接中断、取消和状态复位。
- 关键用户流程仍需通过 Playwright。

### 存储与模型

- 新运行路径通过 settings、config 和应用容器提供，不在模块中推算项目根目录。
- 新增环境变量在 `backend/services/core/settings.py` 中读取并给出默认值，同时在[配置项](./配置项.md)对应分组补一行；不要在 `docker-compose.yml` 里逐项透传，后端通过 `env_file` 读取 `.env`。
- 外部客户端由 `backend/services/core/llm_config.py` 的工厂创建。
- SQL 放在对应 Store 或持久化模块，不进入 router 或聊天编排。
- 索引 schema、嵌入模型或向量维度变化必须提供明确的完整重建路径。

## 交付清单

交付前确认：

- `git diff --check` 没有空白错误。
- 工作区没有意外的运行数据、密钥、报告或构建产物。
- 行为变化有与风险相称的聚焦测试。
- API 变化已审阅并更新 OpenAPI 快照。
- Python 和前端锁文件与依赖声明同步。
- Playwright 包和镜像版本一致。
- `./scripts/check.sh` 全部通过，推送后 GitHub CI（含端到端测试）通过。
- 部署边界变化已运行冒烟测试。

`.github/workflows/ci.yml` 在发布仓库推送后运行 Ruff、Pyright、后端测试、前端检查和 Playwright 端到端测试。`scripts/check.sh` 是推送前的本地基线，另外覆盖 CI 没有的 Docker 镜像构建、`npm audit` 和 Nginx 配置检查。

## Docker 缓存

如果需要回收 Docker 自身的构建缓存，应先确认这些缓存不被其他项目复用，再使用 Docker 命令（例如 `docker builder prune`）；不要用文件系统删除 Docker 数据目录。`docker compose down -v` 会额外删除本项目的 OCR 模型卷，除非明确要重新下载模型，否则不要使用。

## 慢网络与离线迁移

依赖下载只发生在 Docker 构建阶段。网络较慢时，建议在网络较好的机器完成构建，再把镜像导出到目标机器；不建议把 `.uv-cache`、虚拟环境或 `node_modules` 放进项目目录。

构建期的三个下载来源都可以按网络环境覆盖，既可写进 `.env`，也可以临时放在命令前：

| 变量 | 默认值 | 作用 |
| --- | --- | --- |
| `DOCKER_LIBRARY_PREFIX` | `docker.m.daocloud.io/library` | python、node、nginx 基础镜像的来源 |
| `PIP_INDEX_URL` | `https://pypi.org/simple` | Python 包索引 |
| `NPM_REGISTRY` | `https://registry.npmmirror.com/` | 前端 npm 源（`npm audit` 固定用 npmjs.org） |

```bash
# DaoCloud 镜像站偶发 502 时，改用官方源
DOCKER_LIBRARY_PREFIX=docker.io/library docker compose build
```

宿主机能快速访问 PyPI，不代表构建容器也能：Docker 守护进程的代理只用于拉取镜像，不会传给 `RUN` 步骤。实测 WSL2 原生 Docker 下，构建容器直连官方 PyPI 约 100KB/s，清华源约 10MB/s，这时在 `.env` 里设置 `PIP_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple`。

基础镜像版本为 `python:3.12-slim`（`backend/Dockerfile`）、`node:20.20.2-alpine` 和 `nginx:1.31.6-alpine`（`frontend/Dockerfile`），升级时修改对应文件。镜像站拉取失败多为临时错误，重试即可；`scripts/check.sh` 的构建步骤已自带 3 次重试。

若目标机器不能联网，可以同时迁移已构建的镜像：

```bash
# Milvus 镜像必须一并导出，否则目标机器上后端等不到 Milvus 就绪；改过 MILVUS_IMAGE 时按实际名称替换
docker save -o ../ragloom-images.tar \
  ragloom-backend:latest ragloom-frontend:latest \
  docker.1ms.run/milvusdb/milvus:v2.6.0

# 目标机器
docker load -i ../ragloom-images.tar
docker compose up -d
```

镜像、源码和 `storage/` 是三类不同的交付物：源码通过 Git 迁移，镜像用于离线运行，`storage/` 用于业务数据备份。按需选择，不要把三者打成一个公开压缩包。
