# 数据与存储

RAGLoom 的一个知识库不是单个目录或数据库，而是多个存储共同组成的逻辑对象：

| 存储 | 位置 | 保存什么 |
| --- | --- | --- |
| 主业务 SQLite | `storage/data/app_data.sqlite3` | 知识库、文档、任务、父块、账户、会话、运行记录等全部业务数据 |
| 原文件 | `storage/data/<kb_id>/<document_id>/` | 用户上传的不可变原文件 |
| 解析结果 | `storage/mineru_results/` | MinerU 的 Markdown、表格、图片等中间产物 |
| Milvus | Docker 命名卷 `ragloom_milvus_data` | 子块的稠密向量、BM25 稀疏向量和正文 |

四者通过不可变的 `kb_id` 和 `document_id` 关联。本文按“目录布局 → 数据分类 → SQLite 各表 → 文件 → Milvus → 重建与恢复”的顺序说明。

## 1. 存储布局

```text
storage/
  data/
    app_data.sqlite3                     主业务数据库
    .uploads/<token>/                    尚未提交的临时上传
    .index_jobs/<workspace_id>/          索引任务的源文件快照
    <kb_id>/<document_id>/               不可变原文件
  mineru_results/
    <kb_id>/<document_id>/               解析结果
    .index_jobs/<workspace_id>/          索引任务私有的解析结果
  logs/                                  后端文件日志 backend.log 及轮转副本
```

不在 `storage/` 中的两类数据，都不属于业务数据：

- **Milvus 索引**：由独立的 Milvus 容器保存在命名卷 `ragloom_milvus_data`。
- **PaddleOCR 模型**：位于命名卷 `pymodel_paddle_models`。删除该卷会使下一次 OCR 重新下载权重。

**文件属主**：运行容器以 `app` 用户（默认 UID/GID `1000:1000`）写入 `storage/` 和 PaddleOCR 模型卷。镜像中的依赖文件由 root 安装但只读使用；不要把镜像层或 Docker 的内部缓存目录当作项目文件直接删除。

## 2. 权威数据与派生数据

| 分类 | 内容 | 丢失后的处理 |
| --- | --- | --- |
| 权威数据 | 主 SQLite、上传原文件 | 无法从索引完整恢复 |
| 可重建数据 | Milvus collection、`parent_chunks` 表 | 从原文件完整重建 |
| 可复用缓存 | MinerU 结果 | 可重新调用解析服务生成 |
| 运行缓存 | 检索器缓存、查询向量缓存 | 进程重启后自动重建 |

备份的结论：

- 迁移和业务备份应**整体复制 `storage/`**。只复制 `app_data.sqlite3` 不包含原文件。
- Milvus 索引属于派生数据，不需要备份，恢复后对知识库执行完整重建即可。
- 主密钥 `MODEL_API_KEY_ENCRYPTION_KEY` 不在 `storage/` 中，需要单独备份，见[第 7 节](#7-密钥安全与备份恢复)。

## 3. 主业务 SQLite

### 3.1 基本约定

| 项 | 约定 |
| --- | --- |
| 路径 | 默认 `storage/data/app_data.sqlite3` |
| schema 版本 | 当前 v14，由 `backend/services/core/database_schema.py` 的 `CURRENT_DATABASE_SCHEMA_VERSION` 定义，存于 `PRAGMA user_version` |
| 连接 | 统一通过 `backend/services/core/sqlite_connections.py::connect()`，启用 WAL，每个连接都开启外键 |
| 时间 | 带 UTC 偏移的 ISO 文本（`auth_sessions` 例外，使用整数时间戳） |
| 布尔值 | `0/1` |
| 标签、来源等列表 | JSON 文本 |

**版本不一致时不迁移**：schema 版本与当前版本不一致的数据库不会被自动迁移或重置，启动会失败。存量数据按测试数据对待：删除旧数据并重新入库，即删除 `storage/` 后重建。需要保留的内容先备份整个 `storage/`。

### 3.2 表分组总览

16 张表按业务相关性分为六组：

| 分组 | 表 | 说明 |
| --- | --- | --- |
| [知识库与文档](#33-知识库与文档) | `knowledge_bases`、`documents`、`index_jobs`、`parent_chunks` | 知识库本体、文档元数据、索引任务、检索回表用的父块 |
| [账户与权限](#34-账户与权限) | `accounts`、`roles`、`role_knowledge_bases`、`auth_sessions` | 用户、角色、角色的知识库授权、登录会话 |
| [模型配置](#35-模型配置) | `models_config` | 模型服务商配置和加密的 API Key |
| [会话与消息](#36-会话与消息) | `chat_sessions`、`chat_messages`、`chat_session_memory` | 用户可见的对话内容和会话摘要 |
| [问答运行记录与追踪](#37-问答运行记录与追踪) | `chat_runs`、`chat_traces` | 每次问答的耗时统计和处理过程，供运维和排查 |
| [登录记录与审计](#38-登录记录与审计) | `login_events`、`admin_audit_log` | 登录尝试和管理员敏感操作 |

各组之间的主要关系：

```text
knowledge_bases ─┬─< documents ──< parent_chunks
                 ├─< index_jobs
                 ├─< role_knowledge_bases >── roles ──< accounts ──< auth_sessions
                 ├─< chat_sessions ─┬─< chat_messages
                 │                  └── chat_session_memory（一对一）
                 ├─< chat_runs  ── chat_traces（按 run_id 一对一）
                 └─< chat_traces
```

`─<` 表示一对多。带外键的关系都声明了 `ON DELETE CASCADE`；没画出的关联（如 `chat_runs.account_id`、`login_events.account_id`）只是普通列，不建外键，删除时由代码显式清理，见 [3.9](#39-删除与保留规则汇总)。

### 3.3 知识库与文档

| 表 | 主键 | 职责 |
| --- | --- | --- |
| `knowledge_bases` | `kb_id`（uuid） | 名称（唯一，1–80 字）、状态 `active` / `deleting`、分块配置 `chunk_size` / `chunk_overlap`、查询改写开关、当前重建任务 `active_rebuild_job_id`；通用知识库用 `system_key = 'common'` 标识 |
| `documents` | `document_id` | 所属 `kb_id`、文件名、大小、状态、错误信息、当前任务 `index_job_id`、解析方式，以及筛选元数据（文档类型、标签、生效日期）；文件路径按 ID 推导，不入库 |
| `index_jobs` | `id` | `process`（单文档）、`rebuild`（整库）、`delete`（删除文档）任务及其状态；单文档任务记下本次请求的解析方式，发布成功后才写回文档 |
| `parent_chunks` | `(kb_id, document_id, parent_id)` | 固定路线命中子块后用来恢复的完整父块 |

**状态取值**（详细流转见[文档处理与索引](文档处理与索引.md)）：

```text
documents.status   首次索引：processing -> ready / error
                   重新索引：ready -> rebuilding -> publishing -> ready / error
index_jobs.status  queued -> running -> completed / failed / superseded / interrupted
```

**约束**：

- `index_jobs` 用 CHECK 约束保证：`rebuild` 任务没有 `document_id`，`process` 和 `delete` 任务必须有。
- 任务的 `document_id` 不引用 `documents`，保证文档逻辑删除后清理任务仍可执行。
- `parent_chunks` 以 `(kb_id, document_id)` 组合外键引用 `documents`，文档删除时父块级联清除。

**`parent_chunks` 的字段与读写**：字段为 `kb_id`、`document_id`、`parent_id`、`source`、`page`、`content`、`contextual_title`，读写都通过 `backend/services/retrieval/parent_store.py`。它和 Milvus 一样是可重建数据，新旧版本如何切换见 [5.4](#54-发布与版本切换)。

### 3.4 账户与权限

| 表 | 主键 | 职责 |
| --- | --- | --- |
| `accounts` | `id` | 用户名（唯一）、姓名、手机号、bcrypt 密码摘要、状态、所属角色 `role_id` |
| `roles` | `id` | 角色名、描述、菜单权限（JSON 列表）、是否授权全部知识库 `all_knowledge_bases` |
| `role_knowledge_bases` | `(role_id, kb_id)` | 角色的显式知识库授权；`all_knowledge_bases = 1` 时不需要逐库登记 |
| `auth_sessions` | `token_hash` | 服务端登录会话，只保存随机令牌的 SHA-256 摘要，不保存令牌本身 |

`auth_sessions` 的过期规则：

- `expires_at` 是空闲过期时间，每次请求向后滑动（`AUTH_SESSION_TTL_SECONDS`，默认 8 小时）。
- `absolute_expires_at` 是绝对上限（`AUTH_SESSION_MAX_AGE_SECONDS`，默认 7 天），滑动不能超过它。
- 删除账号时会话级联删除；改密码、停用账号时撤销该账号全部会话。
- 过期会话在创建新会话时和应用启动时清理。

### 3.5 模型配置

| 表 | 主键 | 职责 |
| --- | --- | --- |
| `models_config` | `provider_name` | 服务商的接口地址、默认模型、是否启用，以及加密后的 API Key |

API Key 的存储规则：

- 只以 `enc:v1:` 开头的 Fernet 密文保存，包括本地服务的占位 Key；解密失败时报错，不当作明文使用。
- 编辑服务商时 API Key 留空表示保留原值；但如果同时修改了接口地址，必须重新填写 API Key（或清空），否则保存失败（`model_api_key_required`），防止已保存的 Key 被发往新地址。
- 主密钥的生成、更换和备份见[第 7 节](#7-密钥安全与备份恢复)。

### 3.6 会话与消息

| 表 | 主键 | 职责 |
| --- | --- | --- |
| `chat_sessions` | `id` | 会话所属账户、用户名快照、知识库、标题、创建与更新时间 |
| `chat_messages` | 自增 `id` | 每条消息的角色（用户 / 助手）、完整正文、来源快照（JSON） |
| `chat_session_memory` | `session_id` | 每个会话一行：早期对话的滚动摘要，以及摘要覆盖到的最后一条消息 ID |

- 消息和摘要都随会话级联删除。
- 来源快照里保存知识库的显示名称快照，身份始终是 `kb_id`；知识库改名只更新显示名称，不改消息 JSON。
- 跨库的 JSON 证据（例如某条消息引用了被删知识库的来源）不受外键约束，由删除事务显式清理。
- 会话记忆的工作方式见[检索问答与会话](检索问答与会话.md)。

### 3.7 问答运行记录与追踪

两张表在每次问答结束时各写一行，按 `run_id` 一一对应，用途不同：

| | `chat_runs` | `chat_traces` |
| --- | --- | --- |
| 用途 | 运行监控、用户分析的统计数据 | 单次问答的处理过程，供排查 |
| 内容 | 分阶段耗时（检索、重排、上下文、首字、生成、总计）、`status`、重排状态、是否改写、上下文段数、引用数、回答字数、问题前 200 字、错误摘要 | `payload` JSON：各阶段结果、候选与重排分数、片段前 200 字、联网搜索结果、上下文来源；另有完整问题（截断到 4000 字）和用户评价 `feedback` |
| 写入方 | `backend/services/chat/runs.py` | `backend/services/chat/trace.py` |
| 读取权限 | 拥有“运行监控”权限的账号，可看其可读知识库内所有用户 | 接口读取时还要校验知识库权限（含检索片段） |
| 删除会话 | **保留** | 一并删除 |

`chat_runs` 的写入时机：

- 回答成功时，在终态事件发出前写入。
- 取消或失败时，由 `_stream_answer` 的 `finally` 兜底写入；前置阶段就失败的，在 `chat()` 中写入。
- 只保存统计事实。错误摘要是截断到 200 字的“异常类型 + 消息”，不含上游完整响应。
- 写入失败只记警告，不影响回答。

`chat_runs` 不存回答正文和检索文本，它们在 `chat_messages` 里，可用 `session_id` 与 `user_message_id` 关联。`chat_traces` 的字段含义见[检索问答与会话](检索问答与会话.md)的“问答追踪”。

**隐私**：`question_preview` 保存问题前 200 字，会话被删除后仍保留（删除用户时一并删除该用户的记录），直到超过保留期（`CHAT_RUN_RETENTION_DAYS`，默认 90 天）被清理。拥有“运行监控”权限的账号能看到这部分内容，该权限只应授予管理员。

### 3.8 登录记录与审计

| 表 | 写入方 | 内容 | 保留 |
| --- | --- | --- | --- |
| `login_events` | `backend/routers/auth.py` 调用 `backend/services/identity/login_events.py`，每次登录尝试一行 | 时间、用户名、成功与否、失败原因（`invalid_credentials` / `account_not_active` / `rate_limited`）、客户端地址；未知用户名的 `account_id` 为空 | `LOGIN_EVENT_RETENTION_DAYS`（默认 180 天），删除账号时删除其记录 |
| `admin_audit_log` | `backend/services/analytics/audit.py` | 管理员查看用户完整对话等敏感操作：操作者和目标账号的 ID 与用户名快照、动作、详情 | 永久保留，不按保留期清理，删除任何一方账号都不删除 |

- `login_events` 写入失败只记警告，不影响登录。
- `admin_audit_log` 与被读取的对话在同一事务中写入，写不进审计时不返回对话内容。

### 3.9 删除与保留规则汇总

各表的清理分散在不同代码里，按触发事件汇总如下：

| 触发事件 | 清理的表 | 不清理的表 |
| --- | --- | --- |
| 删除会话 | `chat_messages`、`chat_session_memory`（级联），`chat_traces`（显式） | `chat_runs` |
| 删除文档 | `parent_chunks`（级联）；后台任务继续清理 Milvus、原文件和解析结果 | `index_jobs` |
| 删除知识库 | `documents` → `parent_chunks`、`index_jobs`、`role_knowledge_bases`、`chat_sessions` → 消息与摘要、`chat_runs`、`chat_traces`（均级联） | `login_events`、`admin_audit_log` |
| 删除账号 | `chat_sessions`、`chat_messages`、`chat_session_memory`、`chat_runs`、`chat_traces`、`login_events`（显式），`auth_sessions`（级联） | `admin_audit_log` |
| 知识库改名 | 只改 `knowledge_bases.name` | 追踪和消息 JSON 中的名称快照不变 |

按时间自动清理（应用启动时执行）：

| 表 | 规则 |
| --- | --- |
| `chat_runs`、`chat_traces` | 超过 `CHAT_RUN_RETENTION_DAYS`（默认 90 天） |
| `login_events` | 超过 `LOGIN_EVENT_RETENTION_DAYS`（默认 180 天） |
| `index_jobs` | 只裁剪终态任务：超过 `INDEX_JOB_HISTORY_RETENTION_DAYS`（默认 90 天），或超出每库 `INDEX_JOB_HISTORY_MAX_PER_KB`（默认 200 条） |
| `auth_sessions` | 已过期的会话 |
| `admin_audit_log` | 不清理 |

### 3.10 用户分析查询

用户分析的统计直接聚合 `chat_runs`、`chat_traces`、`login_events` 和 `accounts`，没有预聚合表。

- 支撑索引：`chat_runs(account_id, created_at)`、`chat_traces(account_id)`、`login_events` 的时间索引。
- 按天和按小时分组使用 SQLite 的 `localtime`，即后端进程的时区（Compose 中为 `TZ`）。

### 3.11 启动处理

应用启动时依次执行：

```text
校验主密钥 MODEL_API_KEY_ENCRYPTION_KEY（缺失或格式错误时拒绝启动）
  -> 检查 PRAGMA user_version，创建或验证当前 schema
  -> 收紧数据目录和数据库文件权限（0700 / 0600）
  -> 恢复中断的索引任务
  -> 清理临时上传、未登记的 UUID 文档目录和遗留的任务工作区（两个根目录下的 .index_jobs）
  -> 补齐默认角色、admin、通用知识库和模型提供商
  -> 清理任务历史中的孤立文件名
  -> 按保留策略裁剪终态任务
  -> 删除超过保留期的问答运行记录、登录记录和已过期的登录会话
  -> 空闲页足够多时压缩数据库
```

## 4. 文件存储

### 4.1 原文件

- 路径为 `storage/data/<kb_id>/<document_id>/<filename>`。
- 普通上传总是创建新文档，同库同名同内容也可共存。
- 文件名只负责展示、下载名和格式识别。
- 更新解析结果使用原 `document_id` 的重新索引接口，原文件保持不变。
- 预览按 `kb_id` 与 `document_id` 同时校验归属，旧文档删除后不会打开同名新上传。

### 4.2 MinerU 解析结果

- 位于 `storage/mineru_results/`，包含结构化 Markdown、表格和图片等中间产物。
- 知识库重建会尽量复用这些缓存，但解析的源头始终是原文件。

### 4.3 后端日志

- 除标准输出外还写入 `storage/logs/backend.log`，目录可用 `LOG_DIR` 修改。
- 按 `LOG_FILE_MAX_BYTES`（默认 10 MiB）轮转，保留 `LOG_FILE_BACKUPS`（默认 5）个副本；设为 0 则关闭文件日志。
- 目录不可写时只告警，退回标准输出。
- `storage/` 是宿主机挂载目录，容器重建后日志仍在。
- 日志可能含问题与文件名等运行信息，备份整个 `storage/` 时会一并带走。
- 运行监控页的日志面板（`GET /api/ops/logs`）只对超级管理员开放：日志含所有知识库的 ID、文件名和任务信息，无法按查看者可读的知识库过滤。

## 5. Milvus 索引

### 5.1 部署与 collection

- 部署为单容器 Milvus Standalone（内嵌 etcd，本地存储）。
- 全部知识库共享一个 collection，名称为 `{MILVUS_COLLECTION_PREFIX}chunks_v{CURRENT_INDEX_SCHEMA_VERSION}`，当前为 v3，版本号来自 `backend/services/indexing/schema.py`。索引 schema 升级时换用新名称的 collection，不逐条记录版本。
- 向量由项目自行调用 `BAAI/bge-m3` 生成，Milvus 只负责保存和查询。
- 知识库通过不可变的 `kb_id` 关联索引和父块，所以重命名知识库只修改 SQLite，不触碰向量。
- 一致性级别固定为 `Strong`，保证“先写新代、再删旧代”的发布流程立即可见。
- 所有读写都经过 `ChunkIndex` 接口，只有 `milvus_index.py` 直接依赖 pymilvus。

### 5.2 记录结构

| 字段组 | 字段 | 说明 |
| --- | --- | --- |
| 稠密向量 | `id`、`dense` | 1024 维，HNSW，COSINE；维度由 `EMBEDDING_DIMENSION` 给出，必须与嵌入模型一致 |
| 全文检索 | `search_text`、`sparse` | `search_text` 为标题加正文，开启中文 analyzer；`sparse` 由 BM25 Function 从 `search_text` 生成 |
| 正文 | `content` | 子块正文 |
| 归属与定位 | `kb_id`、`document_id`、`source`、`page`、`chunk_index`、`chunk_route` | `source` 是文件名的展示快照 |
| 语境 | `parent_id`、`contextual_title`、可选视觉元数据 | `parent_id` 用于回表 `parent_chunks` |
| 版本 | `generation` | 区分同一文档的新旧两代索引 |

### 5.3 三类索引路线

同一批切片写入同一个 collection，用 `chunk_route` 区分：

| 路线 | 用途 |
| --- | --- |
| `fixed` | 子块负责召回，命中后通过 `parent_id` 恢复完整父块 |
| `structured` | 保留 Markdown、DOCX 或 MinerU 的标题、章节和表格结构 |
| `visual` | 保存图片、图表或复杂表格的视觉分析与 OCR 文本 |

三条路线允许内容重叠，查询阶段负责融合和去重。

### 5.4 发布与版本切换

单个文档的 Milvus 子块和 SQLite 父块一起切换，顺序固定为：

```text
追加新父块 -> 写入新 generation 子块 -> 删除旧 generation 子块 -> 宽限 60 秒后删除旧父块
```

- `parent_id` 每次切分都重新生成，切换期间两版父块并存，命中任一代子块都能回表。
- Milvus 写入失败时新一代子块被撤销，旧版本继续可用；新父块保留到下次发布一并清理。
- 逻辑删除文档时父块先级联清除，后台任务继续清理 Milvus、原文件和解析结果。

完整步骤见[文档处理与索引](文档处理与索引.md)的“索引发布顺序”。

### 5.5 过滤与全文检索

**过滤**：文档类型、标签和生效日期不写入 Milvus。主 SQLite 先算出允许的 `document_id`，再按 `kb_id`、`document_id` 和 `chunk_route` 过滤。过滤表达式只由 `chunk_index.py::build_filter` 生成，所有字符串值统一转义反斜杠和引号。

**BM25 的已知差异**：全文检索由 Milvus 内置 BM25 完成。相比原先的 SQLite FTS5：

- 不再有“严格 AND 优先”的分层查询、短语匹配和对 4 位以上编号词的保护。
- 词频统计（IDF）由整个 collection 共享，一个知识库的数据量会影响另一个库的词权重。

## 6. 重建规则

| 变更 | 是否重建 |
| --- | --- |
| 文档类型、标签、生效日期 | 否，只更新主 SQLite |
| 查询改写开关 | 否，只影响后续提问 |
| 上传同名文件 | 创建新 ID 并独立索引 |
| 重新索引已有文档 | 同一 ID 生成新索引结果，原文件不变 |
| 修改 PDF、DOCX 或图片解析方式 | 重新索引该文件 |
| 修改 `chunk_size` 或 `chunk_overlap` | 完整重建知识库 |
| 修改嵌入模型、维度或索引 schema | 完整重建所有相关知识库（schema 变化会换用新 collection） |

## 7. 密钥、安全与备份恢复

### 7.1 主密钥

- `models_config` 中的 API Key 使用 `MODEL_API_KEY_ENCRYPTION_KEY` 加密。它是标准 Fernet 密钥，生成方式见[配置项](配置项.md)。
- 主密钥不在 `storage/` 中，必须与数据库分别备份；丢失后无法恢复已保存的 API Key。
- 运行时不支持多把密钥或自动轮换。更换主密钥时，先备份 `storage/` 再重建存储，然后在“模型管理”中重新填写 Key。

### 7.2 敏感数据

业务数据库包含密码摘要、用户资料、完整聊天内容和来源，不应提交到仓库，也不应作为普通调试附件共享。

### 7.3 备份与恢复清单

- 备份：整个 `storage/`，加上通过受保护渠道单独保存的 `MODEL_API_KEY_ENCRYPTION_KEY`。
- 恢复后：确认数据库、原文件和加密密钥属于同一套部署。
- Milvus 索引与之不一致时，对知识库执行完整重建。
