# 数据与存储

RAGLoom 的一个知识库不是单个目录或数据库，而是多个存储共同组成的逻辑对象。

## 存储布局

```text
storage/
  data/
    app_data.sqlite3       主业务数据库
    <知识库名称>/           用户上传的原始文件
  mineru_results/          MinerU 结构化解析缓存
  logs/                    后端文件日志 backend.log 及轮转副本
```

向量与全文索引不在 `storage/` 中，由独立的 Milvus 容器保存在命名卷 `ragloom_milvus_data`。PaddleOCR 模型位于 Docker 命名卷 `pymodel_paddle_models`。两者都不属于业务数据。

运行容器以 `app` 用户（默认 UID/GID `1000:1000`）写入 `storage/` 和 PaddleOCR 模型卷。镜像中的依赖文件由 root 安装但只读使用；不要把镜像层或 Docker 的内部缓存目录当作项目文件直接删除。删除模型卷会使下一次 OCR 重新下载权重。

## 权威数据与派生数据

| 分类 | 内容 | 丢失后的处理 |
| --- | --- | --- |
| 权威数据 | 主 SQLite、上传原文件 | 无法从索引完整恢复 |
| 可重建数据 | Milvus collection、`parent_chunks` | 从原文件完整重建 |
| 可复用缓存 | MinerU 结果 | 可重新调用解析服务生成 |
| 运行缓存 | 检索器缓存、查询向量缓存 | 进程重启后自动重建 |

迁移和业务备份应整体复制 `storage/`。只复制 `app_data.sqlite3` 不包含原文件。Milvus 索引属于派生数据，不需要备份，恢复后对知识库执行完整重建即可。

## 主业务 SQLite

默认路径为 `storage/data/app_data.sqlite3`，当前 schema 版本由 `backend/services/core/database_schema.py` 的 `CURRENT_DATABASE_SCHEMA_VERSION` 定义。它保存：

| 表 | 职责 |
| --- | --- |
| `knowledge_bases` | 名称、稳定的 `kb_id`（uuid）、分块配置、查询改写开关和当前重建任务 |
| `documents` | 文件路径、状态、解析方式和筛选元数据 |
| `index_jobs` | `process`、`rebuild`、`delete` 任务及其状态 |
| `parent_chunks` | 固定路线命中后需要恢复的完整父块，主键 `(kb_id, parent_id)` |
| `accounts`、`roles` | 统一账户、状态和权限 |
| `models_config` | 加密后的模型 API Key 和提供商配置 |
| `chat_sessions`、`chat_messages` | 会话、完整消息和来源快照 |
| `chat_runs` | 每次问答的分阶段耗时、结果状态和问题前 200 字，供运行监控使用 |
| `chat_traces` | 每次问答的处理过程追踪：各阶段结果、候选与重排分数、片段前 200 字、联网搜索结果、上下文来源和用户评价，见[检索问答与会话](检索问答与会话.md)的“问答追踪” |
| `chat_session_memory` | 早期对话的增量摘要 |
| `login_events` | 每次登录尝试一行：时间、用户名、结果、失败原因和客户端地址；未知用户名的 `account_id` 为空 |
| `admin_audit_log` | 管理员查看用户完整对话等敏感操作的审计记录 |
| `app_settings` | 自动生成的认证签名密钥等应用设置 |

主库使用 WAL 和统一连接工厂 `backend/services/core/sqlite_connections.py::connect()`。时间以带 UTC 偏移的 ISO 文本保存，布尔值使用 `0/1`，标签和权限列表使用 JSON 文本。

数据库不声明外键。删除账号、知识库或会话时，业务层必须显式清理关联记录；新增关联表时也要同步扩展删除路径和测试。

### 问答运行记录与日志

`chat_runs` 每次问答一行，由 `backend/services/chat/runs.py` 在 `_stream_answer` 的 `finally` 中写入（前置阶段失败时在 `chat()` 中写入）。只保存统计事实：检索、重排、上下文、首字、生成和总耗时，`status`，引用数，以及截断到 200 字的错误摘要（异常类型加消息，不含上游完整响应）。回答正文和检索文本不在此表，仍在 `chat_messages`，可用 `session_id` 与 `user_message_id` 关联。写入失败只记警告，不影响回答。

`chat_traces` 与 `chat_runs` 一一对应（`run_id`），同样在问答结束时写入、按同一保留期清理。与 `chat_runs` 不同，它含检索片段前 200 字和完整问题（截断到 4000 字），因此接口读取时要校验知识库权限；删除会话、账号或知识库时一并删除，知识库改名时同步改名。

隐私：`question_preview` 保存问题前 200 字，会话被删除后仍保留（删除用户时一并删除该用户的记录），直到超过保留期（`CHAT_RUN_RETENTION_DAYS`，默认 90 天）被清理。拥有 `运行监控` 权限的账号能看到所有用户的这部分内容，只应授予管理员。

### 登录记录与审计

`login_events` 由 `backend/routers/auth.py` 在每次登录尝试时写入（`backend/services/identity/login_events.py`），失败原因为 `invalid_credentials`、`account_not_active` 或 `rate_limited`。写入失败只记警告，不影响登录。记录超过 `LOGIN_EVENT_RETENTION_DAYS`（默认 180 天）后随问答记录一起清理；删除账号时删除其登录记录。

`admin_audit_log` 由 `backend/services/analytics/audit.py` 写入，与被读取的对话在同一事务中，写不进审计时不返回对话内容。它保存操作者和目标账号的 ID 与用户名快照，删除任何一方账号都不删除审计记录，也不按保留期清理。

用户分析的统计直接聚合 `chat_runs`、`chat_traces`、`login_events` 和 `accounts`，没有预聚合表；`chat_runs(account_id, created_at)`、`chat_traces(account_id)` 和 `login_events` 的时间索引支撑这些查询。按天和按小时的分组使用 SQLite 的 `localtime`，即后端进程的时区（Compose 中为 `TZ`）。

后端日志除标准输出外还写入 `storage/logs/backend.log`（`LOG_DIR` 可改），按 `LOG_FILE_MAX_BYTES`（默认 10 MiB）轮转，保留 `LOG_FILE_BACKUPS`（默认 5）个副本，设为 0 则关闭文件日志。目录不可写时只告警并退回标准输出。日志可能含问题与文件名等运行信息，备份整个 `storage/` 时会一并带走。`storage/` 是宿主机挂载目录，容器重建后日志仍在。

### 启动处理

应用启动时：

```text
检查 PRAGMA user_version
  -> 创建或验证当前 schema
  -> 按需用新主密钥重加密已保存的模型 API Key（密钥轮换）
  -> 恢复中断的索引任务
  -> 补齐默认角色、admin、通用知识库和模型提供商
  -> 清理任务历史中的孤立文件名
  -> 按保留策略裁剪终态任务
  -> 删除超过 CHAT_RUN_RETENTION_DAYS 的问答运行记录和超过 LOGIN_EVENT_RETENTION_DAYS 的登录记录
  -> 空闲页足够多时压缩数据库
```

schema 版本与当前版本不一致的数据库不会被自动迁移或重置，启动会失败。存量数据按测试数据对待：删除旧数据并重新入库，即删除 `storage/` 后重建。需要保留的内容先备份整个 `storage/`。

模型 API Key 只以加密形式保存，不处理明文存量。主密钥 `MODEL_API_KEY_ENCRYPTION_KEY` 至少 32 个字符，用 `openssl rand -hex 32` 生成。轮换时把新值写入 `MODEL_API_KEY_ENCRYPTION_KEY`，旧值临时写入 `MODEL_API_KEY_PREVIOUS_ENCRYPTION_KEYS`；后端成功启动并完成重加密后清除旧值。

编辑提供商时 API Key 留空表示保留原值；但如果同时修改了接口地址，必须重新填写 API Key（或清空），否则保存失败（`model_api_key_required`），防止已保存的 Key 被发往新地址。

## 原始文件与 MinerU

原文件路径为 `storage/data/<知识库>/<真实文件名>`。真实文件名也是文档来源身份，用于数据库唯一键、索引 `source`、来源展示和下载预览；系统没有独立业务标题字段。

MinerU 结果位于 `storage/mineru_results/`，包含结构化 Markdown、表格和图片等中间产物。知识库重建会尽量复用缓存，但原文件仍是解析源头。

## Milvus 索引

部署为单容器 Milvus Standalone（内嵌 etcd，本地存储）。全部知识库共享一个 collection，名称为 `{MILVUS_COLLECTION_PREFIX}chunks_v{CURRENT_INDEX_SCHEMA_VERSION}`，版本号来自 `backend/services/indexing/schema.py`。索引 schema 升级时换用新名称的 collection，不再逐条记录版本。项目自行调用 `BAAI/bge-m3` 生成向量，Milvus 只保存和查询。

知识库通过不可变的 `kb_id` 关联索引和父块，所以重命名知识库只修改 SQLite，不触碰向量。

一条记录包含：

```text
id + dense（1024 维，HNSW，COSINE）
  + search_text（标题加正文，开启中文 analyzer）+ sparse（由 BM25 Function 从 search_text 生成）
  + content
  + kb_id + source + page + chunk_index + chunk_route
  + parent_id + contextual_title + 可选视觉元数据
  + generation
```

`dense` 维度由 `EMBEDDING_DIMENSION` 给出，必须与嵌入模型一致。collection 的一致性级别固定为 `Strong`，保证先写新代、再删旧代的发布流程立即可见。

文档类型、标签和生效日期不写入 Milvus。主 SQLite 先计算允许的真实文件名，再按 `kb_id`、`source` 和 `chunk_route` 过滤。过滤表达式只由 `chunk_index.py::build_filter` 生成，字符串值（文件名是用户输入）统一转义反斜杠和引号。

更新单个来源时先写入完整的新 generation，成功后删除旧 generation；中途失败则清理新 generation 并保留旧数据。所有读写都经过 `ChunkIndex` 接口，只有 `milvus_index.py` 直接依赖 pymilvus。

全文检索由 Milvus 内置 BM25 完成。相比原先的 SQLite FTS5，已不再有“严格 AND 优先”的分层查询、短语匹配和对 4 位以上编号词的保护；词频统计（IDF）改为整个 collection 共享，一个知识库的数据量会影响另一个库的词权重。

## 父块表

固定路线命中子块后，需要恢复完整父块。父块保存在主 SQLite 的 `parent_chunks`，字段为 `kb_id`、`parent_id`、`source`、`page`、`content`、`contextual_title`，读写都通过 `backend/services/retrieval/parent_store.py`。

发布顺序固定为先写父块表、后写 Milvus，删除顺序相反。两者不是原子操作：Milvus 写入失败时，文档进入 `error`，残留的父块没有对应子块，不会被检索到，重建时被覆盖。

## 三类索引路线

同一批切片写入同一个 Milvus collection，并用 `chunk_route` 区分：

| 路线 | 用途 |
| --- | --- |
| `fixed` | 子块负责召回，命中后通过 `parent_id` 恢复完整父块 |
| `structured` | 保留 Markdown、DOCX 或 MinerU 的标题、章节和表格结构 |
| `visual` | 保存图片、图表或复杂表格的视觉分析与 OCR 文本 |

三条路线允许内容重叠，查询阶段负责融合和去重。

## 重建规则

| 变更 | 是否重建 |
| --- | --- |
| 文档类型、标签、生效日期 | 否，只更新主 SQLite |
| 查询改写开关 | 否，只影响后续提问 |
| 替换同名文件 | 重新索引该文件 |
| 修改 PDF、DOCX 或图片解析方式 | 重新索引该文件 |
| 修改 `chunk_size` 或 `chunk_overlap` | 完整重建知识库 |
| 修改嵌入模型、维度或索引 schema | 完整重建所有相关知识库（schema 变化会换用新 collection） |

## 安全与恢复

`models_config` 中的 API Key 使用 `MODEL_API_KEY_ENCRYPTION_KEY` 加密。该主密钥不在 `storage/` 中，必须与数据库分别备份；丢失主密钥后无法恢复已保存的 API Key。

业务数据库还包含密码摘要、用户资料、完整聊天内容和来源，不应提交或作为普通调试附件共享。恢复后应验证数据库、原文件和加密密钥属于同一套部署；Milvus 索引与之不一致时执行完整重建。

业务迁移必须备份整个 `storage/`，并通过受保护渠道保存对应的 `MODEL_API_KEY_ENCRYPTION_KEY`。
